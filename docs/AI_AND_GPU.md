# AI generation and the GPU path

Status: content generation ("Ask") is implemented in `apps/api` (slice 2). Asset generation is
designed here and not yet implemented. This document is the plan for both, and specifically for
using your own GPUs.

## 1. What exists now

```
Editor "Ask" panel ──POST /api/v1/generations──▶ FastAPI ──▶ TextProvider ──▶ model
        ▲                                            │
        │ proposal (Operation[])                     │ tool calls validated against schemas/operations.json
        └── applyOperations (dry run) ◀──────────────┘
             accept → one undoable transaction
```

- **Tools are the operation catalog.** `schemas/operations.json` is generated from the Zod
  schemas in `packages/project-schema`. Each operation becomes one tool. Adding an operation to
  `project-core` adds a capability to Ask with no Python change. Combat arrived in schema v2 and
  became promptable the same day.
- **Tool calls are collected, not executed.** Each call is validated against its JSON Schema;
  invalid calls go back to the model as errors. The editor then dry-runs the batch through
  `applyOperations`, which enforces referential integrity, and shows a summary. Nothing reaches
  the document without the user pressing Apply.
- **Providers are configuration.** `BEZE_AI_PROVIDER` selects one of:

| Provider | Use | Config |
|----------|-----|--------|
| `anthropic` | Hosted Claude through the official SDK. Best quality for structured generation today. | `ANTHROPIC_API_KEY`, `BEZE_AI_MODEL=claude-opus-5-5`, `BEZE_AI_EFFORT` |
| `openai_compatible` | Any server that speaks the OpenAI chat-completions protocol with tool calling: vLLM, Ollama, LM Studio, TGI. This is how your GPUs plug in for text. | `BEZE_OPENAI_BASE_URL`, `BEZE_AI_MODEL` |
| `fake` | Deterministic output for tests and offline development. | none |

The pipeline, context builder and validation are shared by all three. A provider is ~80 lines.

## 2. Running text generation on your GPUs

Any open-weight model with reliable tool calling works. In practice, as of this writing:

```sh
# one 24 GB card or better
vllm serve Qwen/Qwen3-32B-AWQ --enable-auto-tool-choice --tool-call-parser hermes --max-model-len 32768
# then
BEZE_AI_PROVIDER=openai_compatible BEZE_AI_MODEL=Qwen/Qwen3-32B-AWQ BEZE_OPENAI_BASE_URL=http://gpu-box:8000/v1 pnpm dev:api
```

Ollama also works (`ollama serve`, `BEZE_OPENAI_BASE_URL=http://gpu-box:11434/v1`). Expect
smaller models to make more invalid calls; the validator and the editor's retry-with-errors
loop absorb most of it. Measure with the eval below before committing to a model.

**Eval to run before choosing a model:** a set of 30 prompts (NPC + dialogue, quest with
variables, paint a village, three enemies, a branch on a flag) scored on: batch applies without
integrity errors, the requested things exist by name, no extra players, tool-call rejection
rate, and wall time. The fake provider fixture in `apps/api/tests` is the template.

## 3. Asset generation: the part that needs GPUs most

The goal: "a female swordsman with white hair, a black coat and a katana" becomes a usable
character sheet, a portrait, and later tilesets, in the canonical formats from FOUNDATION.md
section 8.1. This is research-adjacent; the plan is staged so each stage ships value.

### Stage A: portraits (single image, easy)

- Model: an anime-tuned SDXL or Illustrious-family checkpoint on your GPU via ComfyUI or
  Automatic1111's API, or any hosted image API behind the same `ImageProvider` interface.
- Pipeline: prompt template (style anchors, "bust portrait, facing viewer, plain background")
  → generate at 768² → background removal (rembg or BiRefNet) → resize to 256² → PNG → the
  normal upload validation → asset with `origin: 'generated'`.
- Editor: "Generate portrait" on a character. Needs the asset upload path (phase 4), which is
  why assets come before this.

### Stage B: single idle sprite

Same as A with "full body, chibi proportions, front view, pixel art" and a downscale to 32×48
with nearest-neighbour plus palette reduction (pyxelate-style quantisation). Produces
`idle_down` only; the runtime already tolerates any animation frame list, so a one-frame
character plays immediately.

### Stage C: full four-direction walk sheets (the hard one)

Options, in the order to try:

1. **Pose-conditioned generation.** ControlNet OpenPose with a fixed set of 16 skeleton poses
   (4 directions × 4 walk frames) and a reference-image adapter (IP-Adapter) for identity.
   Cheap, runs on one 24 GB card, quality is uneven on hands and feet at 32×48.
2. **Character-sheet LoRA.** Fine-tune a LoRA on a few hundred consistent sheets in the
   canonical layout so the model emits the whole 4×4 grid in one image. Best consistency;
   needs a curated dataset (CC0 packs plus sheets generated by option 1 and hand-filtered).
   This is the first place your GPUs earn their keep for training rather than inference.
3. **Reference-to-animation models** (image-to-video or sprite-animation models) sampled at
   four directions. Promising, moving fast, evaluate periodically.

Every stage ends in the same deterministic post-processor: trim, align feet to the frame
bottom, quantise, assemble into the 4-row sheet, validate. The output is an ordinary asset
that the user can download, edit and re-upload. Assets are never locked to their prompt.

### Stage D: tilesets

Tile generation needs seamless tiling and a coherent palette. Start with a curated CC0
library plus recolouring; then a tile-specific LoRA. Later than A to C.

## 4. Interfaces the GPU work plugs into

```python
class ImageProvider(Protocol):
    name: str
    async def generate(self, req: ImageRequest) -> list[ImageResult]   # bytes + metadata

class GenerationPipeline(Protocol):
    kind: str   # "portrait" | "character_sprite" | "character_sheet" | "tileset"
    async def run(self, job: Job, ctx: PipelineContext) -> GenerationOutput
```

An `ImageProvider` for ComfyUI is a workflow JSON plus a websocket poll; for Automatic1111,
one POST. Both run on your hardware and never see the editor. The API only ever receives
bytes, which go through the same validation as an upload.

## 5. Sizing your GPU box

| Task | Fits on | Notes |
|------|---------|-------|
| Text generation, 32B AWQ | 1 × 24 GB | ~20 tok/s; fine for Ask |
| Text generation, 70B+ | 2 × 24 GB or 1 × 80 GB | Better tool-call reliability |
| SDXL portrait / sprite inference | 1 × 12 GB | seconds per image |
| ControlNet + IP-Adapter sheets | 1 × 24 GB | ~30 s per sheet |
| LoRA training (SDXL) | 1 × 24 GB | hours per run |

Run text and image on separate cards when both are live; the worker's job kinds split by
`--kinds` (FOUNDATION.md section 16.2) so each process pins one GPU.

## 6. What would make it "epic"

Quality comes from three things in this order: a consistent art direction baked into prompt
templates and a LoRA; a strict post-processor so everything lands in the canonical formats the
runtime plays; and a review step in the editor where the user picks from four candidates
instead of accepting one. All three are cheap compared to model work and they are what makes
generated characters feel like they belong in the same game.
